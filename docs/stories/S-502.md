## Goal
After a new bulletin is added, each confirmed subscriber gets **at most one** email, and only if something
relevant to them changed. The job must be safe to run twice, must have a dry-run mode, and for the first
three months must be started by the owner by hand.

## Who gets an email
For a subscriber with (`line`, `area`, `chart`, optional `priorityDate`) and a new period P with previous period P−1:
1. For each chart the subscriber follows (`both` = two charts), take `now = getCutoff(view(P), …)` and `before = getCutoff(view(P−1), …)`.
2. **Send** when, for at least one followed chart, `describeChange(now, before)` is not `unchanged`,
   **or** the subscriber gave a priority date and `priorityDateStatus(priorityDate, before) !== 'current'` while
   `priorityDateStatus(priorityDate, now) === 'current'` (their date became current).
3. Do **not** send when: P−1 is missing from the data; the new month is not verified; nothing changed.

## Email content (plain text; build it from a pure function)
```
Subject: <code> <area>: <chart name> <label> in the <Month Year> Visa Bulletin
   (when their date became current: "<code> <area>: your priority date is now current on <chart name>")

<Month Year> Visa Bulletin, <code> <area name>

<Chart name>: <old> → <new> (<label>)          one line per followed chart, including unchanged ones
[Your priority date <date> is now earlier than the <chart name> cut-off.]       only when true
[Whether USCIS accepts the Dates for Filing chart this month: <site>/… or the USCIS page]   when Dates for Filing is involved

Verified against the official bulletin: <official URL>
Full history: <site>/priority-dates/<line>/<area>/

This is information, not legal advice. Being current does not guarantee approval or a date.
Unsubscribe: <link>   ·   Delete my data: <link>
<POSTAL_ADDRESS>
```
Headers: `List-Unsubscribe: <unsubscribe URL>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.

## Files to create
```
worker/src/digest.js          selectRecipients({ subscribers, current, previous }) → [{ subscriber, changes, becameCurrent }]   (pure)
worker/src/digestEmail.js     digestEmail({ subscriber, changes, becameCurrent, period, siteUrl, officialUrl, unsubscribeUrl, deleteUrl, postalAddress }) → { subject, text, headers }   (pure)
worker/src/runDigest.js       runDigest({ store, mailer, bulletins, period, dryRun, now }) → { wouldSend: n, sent: n, skipped: n }
test/worker/digest.test.js, digestEmail.test.js, runDigest.test.js
```
Extend the `Store` interface from S-501 with `listActive()` and `markSent(id, period)` / `wasSent(id, period)`
(a `sent` table keyed by subscription id + period; add it to `worker/schema.sql`).

## Steps
1. `digest.js` and tests: unchanged → no send; advance → send; retrogression → send; became current → send with the
   flag; missing previous month → nobody; subscriber following `both` with one chart changed → one email listing both charts.
2. `digestEmail.js` and tests: subject for each case; both links present; the disclaimer sentence present; the postal
   address present; no HTML; the words `will`, `expect`, `soon`, `congratulations` never appear.
3. `runDigest.js`: for each recipient, skip if `wasSent(id, period)`; in dry-run mode collect the would-send list
   (subscription id, line, area — **not** the email address) and send nothing; otherwise send, then `markSent`.
   A send failure for one subscriber is counted and does not stop the others. Tests: running twice sends nothing the
   second time; dry run sends nothing; a failing mailer does not mark as sent.
4. Trigger: add to `worker/src/index.js` an authenticated `POST /admin/digest { period, dryRun }` that requires a secret
   header (`ADMIN_TOKEN`, platform secret). Default `dryRun: true`. There is **no** automatic trigger in this story.
5. `worker/README.md`: the owner procedure — after merging the month's data and deploying: (1) dry run, read the count;
   (2) real run. Note: "for the first three months, always do both steps by hand".
6. The worker needs the bulletin data: it fetches `<site>/data/bulletins/<period>.json` and the previous month from the
   live site (same origin as the links). Document that the site must be deployed before the digest runs.
7. `npm run check`.

## Acceptance
- [ ] One email per subscriber per period at most; re-running sends nothing twice (test).
- [ ] An email goes out only when the subscriber's line changed or their date became current under a followed chart.
- [ ] The email shows old → new, the movement label, the verification statement and link, unsubscribe and delete links, and the postal address.
- [ ] One-click unsubscribe headers present.
- [ ] Dry-run prints the would-send list without addresses and sends nothing.
- [ ] No automatic sending; the trigger needs the owner's secret; documented procedure exists.
- [ ] `npm run check` green; nothing deployed; no email sent.

## Pitfalls
- Never send for an unverified month. A wrong alert email cannot be taken back.
- "Became current" is a statement about a cut-off, not about the person's case: keep the wording to the sentence in the template.
- Do not log email addresses, even in dry run.
