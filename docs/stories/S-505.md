## Goal
Make sure every email the site sends is lawful and deliverable: sender identity and a physical postal
address in each message, authenticated sending domain, a retention statement, a way to handle complaints,
and a checklist that is run before every send.

## Owner decisions needed (write the answers into `docs/EMAIL.md`, section "Settings")
1. The sending domain and From address (for example `alerts@<domain>`). Not a personal address.
2. A physical postal address to print in every email (U.S. CAN-SPAM requires one; a P.O. box or a registered
   commercial mail address is acceptable). This is a public value once emails go out.
3. The email delivery provider (decision D9 suggests one; the owner creates the account).
4. A monitored reply/complaints address.

## Agent part (can be prepared before the owner answers; leave placeholders `{{…}}`)
Create `docs/EMAIL.md` with these sections:
1. **Settings** — the four values above (placeholders until the owner fills them).
2. **DNS records to add** — a table with one row each for SPF, DKIM and DMARC: record type, host, and "value: copy from
   the provider's dashboard". State that the exact values come from the provider and must not be invented here.
   Recommended DMARC start: policy `none` with a reporting address, tightened after two clean months (mark this as a
   recommendation for the owner to confirm with the provider's documentation).
3. **What every email contains** — sender name, the reason the person receives it ("You asked VisaPulse for alerts
   about <category> <area>"), one-click unsubscribe link and header, delete-my-data link, the postal address, the
   not-legal-advice line. No tracking pixels, no link tracking, no marketing content.
4. **Retention** — unconfirmed sign-ups deleted after 7 days; active subscriptions kept until unsubscribed; unsubscribing
   deletes the row; send logs keep subscription id and period only.
5. **Complaints and bounces** — hard bounce → delete the subscription; spam complaint → delete and never re-add; a reply
   asking to stop → delete within one working day; where the provider shows these.
6. **Pre-send checklist** (run before every digest):
   - [ ] the month is verified and spot-checked (RUNBOOKS RB2 step 3)
   - [ ] the site is deployed and shows the month
   - [ ] dry run done; recipient count is plausible compared with last month
   - [ ] one test email sent to the owner's own address and read on a phone
   - [ ] unsubscribe link in that test email works
   - [ ] then, and only then, the real run
7. **If a wrong email went out** — stop further sends; publish a correction on the bulletin page and the changelog (S-608);
   send one correction email only to those who received the wrong one.

Also:

  statement from section 4 in the same words.
- `docs/RUNBOOKS.md`: add **RB11 Email complaints** pointing to `docs/EMAIL.md` sections 5 and 7.
- Replace the `{{POSTAL_ADDRESS}}` placeholder used by S-501/S-502 with a platform variable `POSTAL_ADDRESS`
  (never hard-code the address in the repository).

## Acceptance

- [ ] The privacy page carries the retention statement (when alerts are on).
- [ ] RUNBOOKS RB11 exists.
- [ ] The digest email template includes sender identity and the postal address from a variable (test in S-502 covers it).
- [ ] Owner has filled the Settings section and confirmed the DNS records are live (until then the story stays `BLOCKED`).

## Pitfalls
- This is a checklist, not legal advice to the owner. Add the sentence: "Rules differ by country (for example GDPR for
  EU residents, CASL for Canada). If subscribers outside the U.S. become common, ask a lawyer."
- Never put the owner's home address in a file without being told to.
