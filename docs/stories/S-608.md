## Goal
A site that asks to be trusted should show its corrections. `/changelog/` lists every data correction
(month, what changed, why, source) and notable feature releases, generated from one JSON file. Publishing our
own mistakes is also a growth asset: it is what the trust positioning rests on.

## Data file `data/changelog.json`
An array, newest first:
```json
[
  { "date": "2026-11-16", "type": "release", "title": "Priority-date checker",
    "text": "Check a priority date against both charts. Runs in your browser.", "path": "/check/" },
  { "date": "2026-11-16", "type": "correction", "period": "2003-06", "title": "June 2003 employment cut-offs",
    "text": "An earlier third-party source listed family cut-offs under employment rows. Replaced with the official values.",
    "sourceUrl": "https://travel.state.gov/…" }
]
```
Rules: `date` ISO; `type` is `release` or `correction`; `title` 5–100 characters; `text` 10–400 characters, plain text;
`path` (optional) starts with `/`; a `correction` requires `period` (a valid period) and `sourceUrl` starting with
`https://travel.state.gov/` or `https://web.archive.org/`; no other keys.

## Steps
1. `validateChangelog(data)` → `string[]` with the rules above, plus "entries are sorted newest first". Tests: valid
   file; one failing example per rule.
2. `scripts/validate-data.mjs`: load and validate the file; problems go into `errors`.
3. Seed the file with **only entries you can verify from `docs/LOGBOOK.md`**:
   - releases: static site with a page per month and per category × area (2026-11-16); priority-date checker (2026-11-16);
   - correction: June 2003 (the logbook entry of 2026-11-16 15:15 and `docs/data/CROSSCHECK.md` document it; use the
     official URL from `data/bulletins/2003/2003-06.json` → `bulletin.officialSourceUrl`).
   Do not add anything else.
4. `changelogPage({ site, changelog })`: `<h1>Changelog and corrections</h1>`; lede "Every correction to the data and
   every notable change to the site. If you find a number that differs from the official bulletin, tell us and it will
   be listed here."; two sections, **Corrections** first, then **Releases**; each entry shows the date
   (`formatDate`), title, text, the bulletin month as a link to its page (corrections), and the source link.
   When there are no corrections: "No corrections so far."
5. Footer navigation: "Changelog" after "Open data". Register the page in the build.
6. Feed: add corrections to `/feed.xml` as entries titled `Correction: <title>` with `<updated>` = the entry date and a
   link to `/changelog/` (id = link + `#` + date + `-` + period). Bulletin entries stay as they are; order the whole feed by date, newest first.
7. `docs/RUNBOOKS.md` RB5 ("A number looks wrong in production"): add step 5: "Add a `correction` entry to
   `data/changelog.json` (date, month, what changed, why, official source). Required for every correction."
8. `npm run check`.

## Pitfalls
- A correction must name its official source. "We noticed an error" without a source is not a correction entry.
- Keep entries short and factual; no marketing language in release notes.
