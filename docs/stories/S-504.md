# S-504 Follow-by-feed page (`/alerts/`)

| | |
|---|---|
| Status | READY (do this before the other alert stories: it needs no backend) |
| Size | S |
| Difficulty | Routine |
| Phase | 4 Alerts and retention |
| Needs | nothing |

## Goal
Give visitors a way to hear about each new bulletin **today**, before email alerts exist: the site already
publishes a feed (`/feed.xml`). Explain in plain words how to follow it, and say that email alerts are planned.
This page is the destination for every "get notified" link in our posts.

## Behaviour
- The page and all links to it exist **only when the site has a feed** (`site.hasFeed`, which is true when `SITE_URL` is set).
- No third-party embeds, no sign-up form, no endorsement of a specific product.

## Files to touch
`src/site/format.js` (`urls.alerts = '/alerts/'`), `src/site/pages.js`, `scripts/build-site.mjs`, `test/site.test.js`.

## Steps
1. `src/site/pages.js`: export `alertsPage({ site })`. Content (use these words; `<feed>` = `${site.siteUrl}${urls.feed}`):
   - `<h1>Get told when a new Visa Bulletin is out</h1>`
   - Lede: "The State Department publishes each bulletin around the middle of the month before it takes effect. We add
     it here as soon as we have checked it, and our feed updates at the same moment."
   - `<h2>Follow the feed</h2>` — "Copy this address into any feed reader:" then the address inside
     `<input type="text" readonly value="<feed>" aria-label="Feed address">` and a normal link to it.
     "A feed reader is an app that collects updates from sites you choose. Most are free, and you do not give us your
     email address or any other detail."
   - `<h2>Prefer email?</h2>` — "Some services turn a feed into an email. If you use one, give it the feed address above.
     We do not run or recommend a particular service. Our own email alerts, with a confirmation step and one-click
     unsubscribe, are planned."
   - `<h2>What you will get</h2>` — a list: one entry per bulletin; the month, a one-line summary of movement, and a link
     to the full tables; nothing else, no marketing.
   - A closing `muted` paragraph: "We never predict dates. An alert only tells you a bulletin was published."
   Title: `Visa Bulletin alerts: follow new bulletins by feed`. Description: `Get told when a new Visa Bulletin is
   published: follow the VisaPulse feed in any reader. No sign-up, no email address needed.`
2. `scripts/build-site.mjs`: add the page to `pages` only when `site.hasFeed`.
3. Links, each wrapped in `site.hasFeed ? … : ''`:
   - home page call-to-action row: a quiet button "Get new-bulletin alerts";
   - every bulletin page, inside the pager section or just above it: "Get told when the next bulletin is out";
   - footer navigation in `layout.js`: "Alerts" before "Feed".
4. `npm run check`, then `SITE_URL=https://example.org npm run build && npm run check:site`.

## Tests to add (`test/site.test.js`)
- With the default `site`: no page contains `/alerts/`.
- With `liveSite`: `alertsPage` renders the `<h1>` and contains `https://example.org/feed.xml`; the home page contains a
  link to `/alerts/`.

## Acceptance
- [ ] `/alerts/` exists only when `SITE_URL` is set; no link to it otherwise (default build passes `check-site`).
- [ ] The page explains feed readers and feed-to-email generically, with no product named and no embed.
- [ ] It says email alerts are planned and promises nothing about dates.
- [ ] Linked from the home page, bulletin pages and the footer.
- [ ] Both builds (with and without `SITE_URL`) pass `npm run check:site`.

## Pitfalls
- The existing test for the home page with `liveSite` renders it without registering `/alerts/`; that is fine for the
  renderer test, but the **build** must register the page or `check-site` reports a broken link.
- When S-503 (email sign-up form) ships, this page gains the form; keep the structure simple so that is easy.
