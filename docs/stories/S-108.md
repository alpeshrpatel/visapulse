## Goal
After the owner's bulk download, many months will have failed to parse because old bulletins use row labels,
columns or cell formats the parser has never seen. Make every month from 2002-01 onward either a verified
record, or a named entry in `docs/data/UNPARSED.md` with the reason. Nothing is guessed.

## Before you start
```bash
ls data/bulletins/*/*.json | wc -l      # must be far more than 3
ls .cache/official/*.html | wc -l       # the downloaded official pages; must be in the hundreds
```
If either shows only a handful of files, the backfill has not been run here. **Stop**: set this story back to
`READY`, note it in the logbook, and take the next story in the queue. Do not download anything.

## Context
- `src/lib/parseBulletin.js` turns one official page into a record. It throws `BulletinParseError` on anything
  it does not recognise. The tables to extend are `AREA_PATTERNS` and `CATEGORY_PATTERNS` near the top.
- `src/lib/extractTables.js` gives `extractTables(html)` → `[{ rows: string[][], before: string }]`.
- `scripts/build-data.mjs` parses every cached page listed in `data/sources/manifest.json`, writes records,
  and prints a "Not verified" list. It uses no network.
- `test/parseBulletin.test.js` has three fixture tests (2003-06, 2015-10, 2025-06). Copy their pattern.
- `.cache/` is ignored by git. A page becomes a test fixture only by copying it into `test/fixtures/official/`.

## Out of scope
Changing the schema. Display names for new rows (that is S-212). Removing the legacy data (S-109).

## Files to touch
`src/lib/parseBulletin.js`, `scripts/build-data.mjs`, `test/parseBulletin.test.js`, `test/fixtures/official/*.html` (new),
`docs/data/UNPARSED.md` (generated), `docs/data/CROSSCHECK.md` (generated), `docs/LOGBOOK.md`.

## Steps
1. **Make `build-data` write the unparsed list.** In `scripts/build-data.mjs`, after the loop, write
   `docs/data/UNPARSED.md` every run: a header line, the date is **not** included (keeps the file stable), then a table
   `| Period | Reason |` with one row per failure, sorted by period. Also add one row
   `| <period> | no archived snapshot |` for every month between `2002-01` and the newest manifest period that has
   no manifest entry (use `periodRange` from `src/lib/period.js`). When there are no rows, write "Every month is verified."
2. Run `node scripts/build-data.mjs > /tmp/build-data.log 2>&1; tail -n 80 /tmp/build-data.log`
   (use your scratch directory instead of `/tmp` if you have one). Read the failure list.
3. Group the failures by message. Typical groups: `unrecognised employmentBased row "…"`, `unrecognised cell "…"`,
   `expected 1 familySponsored table(s), found 0`, `cannot tell family from employment`.
4. For each group, **read the official page before changing the parser**. Print the tables of one failing month:
   ```bash
   node -e "import('./src/lib/extractTables.js').then(({extractTables})=>{const h=require('fs').readFileSync('.cache/official/2006-03.html','utf8');for(const t of extractTables(h))if(t.rows.length>=4)console.log(JSON.stringify(t.rows.slice(0,14),null,1))})"
   ```
   Find the row or cell in the output and confirm what it means from the page's own text.
5. Extend the parser, smallest change first:
   - New row label → add one `[regex, key]` pair to `CATEGORY_PATTERNS`. Keys already known to the site:
     `EB5`, `EB5NRC`, `EB5RC`, `EB5TEARC`, `EB5Unreserved`, `EB5Rural`, `EB5HighUnemployment`, `EB5Infrastructure`,
     `EB3OW`, `EB4SR`. For a row with no key yet (for example Schedule A workers, 2005–2007) invent a clear key
     such as `EBScheduleA` and list it in the logbook for S-212.
   - New area column → add one pair to `AREA_PATTERNS` with a camelCase key (for example `elSalvadorGuatemalaHonduras`, `vietnam`,
     `dominicanRepublic`). The generic fallback already keeps unknown columns with a warning; replace each warned column
     with an explicit pattern.
   - New cell format → extend `parseCell` only if the page's meaning is unambiguous. If a cell is a footnote mark,
     blank, or anything you cannot read with certainty, **do not parse that month**. It stays in `UNPARSED.md`.
6. For each era you fixed, copy one page into the fixtures and add a test:
   ```bash
   cp .cache/official/2006-03.html test/fixtures/official/2006-03.html
   ```
   Add the period to the list in the test `fixtures are the exact official bytes pinned in the manifest`, and add a
   test that asserts **three cells you read yourself on the page** plus the list of area keys. Required fixtures at minimum:
   one month from 2002; one from the 2005–2007 Schedule A period; one from 2008–2014; one month with an extra area
   column; one from the 2019–2022 EB-5 regional-center period.
7. Re-run `node scripts/build-data.mjs`. Repeat steps 3–6 until the remaining failures are months you have decided
   not to parse. Never use `--force` in this story: no existing record should change. If one would, stop and log it.
8. Do **not** change `PARSER_VERSION` unless the output for an already-written record changes (it should not).
9. Run `npm run data:validate` and `npm run data:crosscheck`, then `npm run check`.

## Pitfalls
- A regex that is too loose will silently map a different row to an existing key. Anchor every pattern with `^` and `$`
  unless the label has a variable tail, and re-run all fixture tests.
- Two-digit years are resolved in `parseCell` by "not later than the bulletin month". Do not change that rule.
- Old pages put the group name ("Family", "Employment-Based") in a label row. The parser already handles one layout;
  if you meet another, extend the `groupText` logic and add a fixture for it.
- The Dates for Filing chart must not appear before `2015-10`.
