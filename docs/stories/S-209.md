## Goal
Prove, with recorded evidence, that the site is usable by keyboard and screen reader, meets WCAG AA contrast
in both themes, prints sensibly, and is fast on a phone. Fix what fails.

## Already done (do not repeat)
No horizontal overflow at 375/768/1280; both themes render; 0.9 kB gz of JavaScript on ordinary pages.

## Files to touch
`test/contrast.test.js` (new), `src/site/site.css`, `src/client/planner.css`, possibly `src/site/layout.js`,
`src/site/components.js`, `src/site/chart.js`, `docs/LOGBOOK.md`.

## Part A — contrast, as a permanent test (no browser needed)
1. Create `test/contrast.test.js`. It reads `src/site/site.css` as text and extracts the custom properties of the light
   theme (the first `:root { … }` block) and the dark theme (the `:root[data-theme='dark'] { … }` block) with a regular
   expression for `--name: #rrggbb`.
2. Implement the WCAG relative-luminance formula in the test file:
   channel `c/255`; `c <= 0.03928 ? c/12.92 : ((c+0.055)/1.055) ** 2.4`; `L = 0.2126 R + 0.7152 G + 0.0722 B`;
   ratio = `(lighter + 0.05) / (darker + 0.05)`.
3. Assert for **both** themes:

   | Foreground | Background | Minimum |
   |---|---|---|
   | `--ink`, `--ink-2`, `--ink-3` | `--paper` and `--surface` | 4.5 |
   | `--accent` (links) | `--paper` and `--surface` | 4.5 |
   | `--advance` | `--advance-surface` | 4.5 |
   | `--retro` | `--retro-surface` | 4.5 |
   | `--warn-ink` | `--warn-surface` | 4.5 |
   | `--head-ink` | `--head` | 4.5 |
   | `--series-1` … `--series-5` (chart lines) | `--surface` | 3.0 |
4. Run `npm test`. For each failing pair, change the **foreground** colour in `site.css` by the smallest step that passes
   (darken in light theme, lighten in dark theme). Keep the hue. Change both dark-theme blocks identically (the
   `@media (prefers-color-scheme: dark)` block and the `:root[data-theme='dark']` block hold the same values).
5. Record every changed colour (old → new, ratio before → after) in the logbook.

## Part B — keyboard and structure (browser needed)
For each page: `/`, `/visa-bulletin/june-2025/`, `/priority-dates/eb2/india/`, `/check/`, `/planner/`:
1. Press Tab from the top. The first stop must be "Skip to content" and activating it must move focus to the main content.
2. Every link, button, form control and scrollable table region must be reachable, in visual order, with a visible focus ring.
3. The chart switch buttons (Final Action / Dates for Filing) must toggle with Enter and Space and expose `aria-pressed`.
4. Nothing may trap focus. Write down any control you could not reach or see focus on, then fix it in CSS or markup.

## Part C — screen-reader semantics (read the page structure with `read_page`, or inspect the HTML)
1. One cut-off table: column headers are `<th scope="col">`, row headers `<th scope="row">`, the scroll wrapper has
   `role="region"` and an `aria-label`. Movement chips carry hidden text ("moved forward", "moved back").
2. One chart: the `<svg>` has `role="img"` and `aria-labelledby` pointing at a `<title>` and `<desc>`; and the same
   numbers are available as a table on the page (the "Month-by-month history" table). If a chart page has no table
   equivalent, add a sentence linking to the history table.

## Part D — motion and print
1. `site.css` must not animate anything outside `@media (prefers-reduced-motion: no-preference)`. Search for
   `transition` and `animation` in both CSS files and move any you find inside that media query.
2. Print preview of a bulletin page (or emulate print media): navigation, theme button, call-to-action buttons and the
   feedback form hidden; both charts' tables visible; the source line and the footer disclaimer present. Fix in the
   `@media print` block at the end of `site.css`.

## Part E — performance
1. Build with `SITE_URL=https://example.org npm run build`, then serve `dist/` (`npm run dev`).
2. Try `npx --yes lighthouse http://localhost:4321/ --only-categories=performance,accessibility,best-practices,seo --form-factor=mobile --quiet --chrome-flags="--headless"`
   for the five pages in part B. If Lighthouse cannot be installed or run in this session, do not invent scores: record
   "Lighthouse not run" and instead record for each page the HTML size (gzip), the number of requests and the JS size.
3. Targets: every category ≥ 95 on all pages, except planner performance ≥ 90. If the planner misses, note it: that is the
   trigger for S-210.

## Pitfalls
- Do not lower a contrast threshold to make the test pass.
- The planner's own stylesheet (`src/client/planner.css`) reuses variables from `site.css`; a colour fix there is usually a
  fix to the variable, not to the planner file.
- A focus ring exists globally (`:focus-visible`). If a control hides it, the cause is usually `outline: none` in a
  component rule; remove that rule rather than adding a second ring.
