# S-212 Rows and areas from other eras

| | |
|---|---|
| Status | READY (after S-108) |
| Size | S |

## Goal
Old bulletins contain rows and columns today's bulletin does not (Schedule A workers, EB-5 regional-center
lines, El Salvador/Guatemala/Honduras, Vietnam, Dominican Republic …). Every such key must have a proper
display name, appear correctly on its bulletin page, and be explained on the methodology page. A test must
fail if a record ever contains a key with no display name.

## Context
- `src/lib/labels.js`: `AREAS` (the five areas with their own pages) and `LINES` (the lines with their own pages).
- `src/site/components.js`: `OTHER_ROW_NAMES` maps printed rows that are not site lines to a display name;
  `cutoffTable` shows extra area columns using the label exactly as printed (`view.areas[key]`, often ALL CAPS).
- `findLine` in `src/lib/dataset.js` follows `line.candidates` to join eras (see `EB5Unreserved`).

## Out of scope
Creating new pages for historical rows or areas. They appear on bulletin pages only.

## Files to touch
`src/lib/labels.js`, `src/site/components.js`, `src/site/pages.js` (methodology text), `test/dataset.test.js`.

## Steps
1. List every key present in the verified records:
   ```bash
   node -e "import('./src/lib/dataset.js').then(({loadDataset})=>{const d=loadDataset({officialDir:'data/bulletins'});const a=new Set(),c=new Set();for(const p of d.periods){const v=d.get(p);Object.keys(v.areas).forEach(k=>a.add(k));for(const g of Object.values(v.categories))Object.keys(g).forEach(k=>c.add(k))}console.log([...a].sort().join(' '));console.log([...c].sort().join(' '))})"
   ```
2. `src/lib/labels.js`: add and export
   ```js
   /** Areas that appear only in some bulletins and have no page of their own. key → display name */
   export const HISTORICAL_AREAS = Object.freeze({ /* e.g. vietnam: 'Vietnam', elSalvadorGuatemalaHonduras: 'El Salvador, Guatemala, Honduras' */ })
   /** Rows that are not one of the site's lines. key → display name */
   export const HISTORICAL_ROWS = Object.freeze({ /* move OTHER_ROW_NAMES here and add the new keys */ })
   /** @param {string} key */ export const areaName = (key) => areaByKey(key)?.name ?? HISTORICAL_AREAS[key] ?? null
   /** @param {string} key */ export const rowName = (key) => lineByKey(key)?.code ?? HISTORICAL_ROWS[key] ?? null
   ```
   Fill both maps for **every** key from step 1 that is not in `AREAS` / `LINES`. Take each display name from the label
   printed in the record (`view.areas[key]`, `category.label`), written in normal capitalisation. Do not invent a
   meaning for a row you have not read; if a label is unclear, open that month's record and its official source link.
3. `src/site/components.js`: delete `OTHER_ROW_NAMES`; in `cutoffTable` use `rowName(key) ?? category.label` for the row
   code and `areaName(key) ?? view.areas[key]` for extra column headers.
4. Decide lineage only where the official label proves it. If S-108's logbook shows a row that is the same line under an
   older printed name, add its key to that line's `candidates` in `LINES` and extend `line.note` with one plain sentence.
   When in doubt, do not join: a separate historical row is always correct.
5. Methodology page (`staticPages` in `src/site/pages.js`), section "Reading rules we apply": add one bullet listing which
   historical rows feed which current line (generated from `LINES` entries that have more than one candidate), and one bullet
   saying historical rows and areas with no current equivalent are shown on their bulletin pages under their own names.
6. `test/dataset.test.js`: add the test "every key in every record has a display name": loop all periods, all area keys
   and all category keys; assert `areaName(key)` and `rowName(key)` are non-null.
7. `npm run check`; open one bulletin page from each era that has an extra row or column and look at the table.

## Acceptance
- [ ] Every area and category key in any record has a display name; the new test proves it.
- [ ] Bulletin pages show historical rows and columns under readable names (no ALL CAPS headers, no internal keys).
- [ ] The methodology page explains the joins and the stand-alone historical rows.
- [ ] No lineage was added without the official label supporting it (each join is listed in the logbook with the label text).
- [ ] `npm run check` green; three historical bulletin pages checked at 375 and 1280.

## Pitfalls
- Extra columns make tables wider. The table scrolls inside `.table-scroll`; confirm the page itself does not scroll sideways.
- `summariseMovement` and the per-line pages loop over `LINES` and `AREAS` only. That is intended; do not add historical keys there.
