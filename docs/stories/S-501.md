## Goal
A tiny service that stores email-alert subscriptions with double opt-in. This story delivers the code and
tests so that deployment is a single owner step later. Nothing is deployed, no email is sent, and no account
is created in this story.

## Design (decision D9 names the stack: Cloudflare Worker + D1 database + an email API)
The logic is written against two small interfaces so it runs under `node:test` with fakes:
```js
/** @typedef {{ insert(row), getByEmailHash(hash), getByToken(kind, tokenHash), update(id, fields), remove(id), purgeUnconfirmed(olderThanIso), countRecentByIp(ipHash, sinceIso) }} Store */
/** @typedef {{ send(message: { to: string, subject: string, text: string, headers?: Record<string,string> }): Promise<void> }} Mailer */
```

### Data stored per subscription (nothing else, ever)
`id`, `email`, `emailHash` (SHA-256 of the lower-cased email), `line` (a `LINES` key), `area` (an `AREAS` key),
`chart` (`finalActionDates` | `datesForFiling` | `both`), `priorityDate` (ISO date or empty), `status`
(`pending` | `active`), `confirmTokenHash`, `manageTokenHash`, `createdAt`, `confirmedAt`, `ipHash` (SHA-256 of IP + a
server secret, kept only to rate-limit, cleared on confirmation).

### Endpoints (all JSON; all inputs validated; all responses the same shape `{ ok: boolean, message: string }`)
| Method and path | Behaviour |
|---|---|
| `POST /subscribe` `{ email, line, area, chart, priorityDate?, challenge }` | Validate. Verify the bot challenge token through an injected `verifyChallenge(token, ip)` function. Rate limit: at most 5 requests per IP hash per hour. If the email already has an active or pending row for the same line and area, do **not** reveal that: respond with the same success message. Otherwise insert `pending`, send the confirmation email. |
| `GET /confirm?token=…` | Look up by hashed token. If pending and younger than 7 days: set `active`, clear `ipHash`, set `confirmedAt`. Respond with a small HTML page. Unknown or expired token → a neutral "this link is no longer valid" page. |
| `GET` or `POST /unsubscribe?token=…` | Delete the row (delete, not deactivate). Supports one-click unsubscribe (`POST` with `List-Unsubscribe=One-Click`). |
| `POST /delete` `{ email }` | Always answer "If that address is subscribed, we have sent it a link." If rows exist, email a link that deletes every row for the address. |

### Security rules
- Tokens: 32 random bytes from `crypto.getRandomValues`, hex-encoded; only the SHA-256 hash is stored.
- Compare token hashes with a constant-time comparison.
- Email: trim, lower-case, at most 254 characters, one `@`, a dot in the domain, no spaces or control characters.
- `line`, `area`, `chart` must be in the allowed lists (import from `src/lib/labels.js`). `priorityDate` must pass `isIsoDate` and not be in the future (the handler receives `now` as a parameter).
- Body size limit 2 kB; `Content-Type` must be `application/json` for POSTs; CORS allows only the configured site origin.
- No email address, token or IP ever appears in a log line.
- Secrets (`MAIL_API_KEY`, `IP_SALT`, `CHALLENGE_SECRET`) are read from the platform environment only. None in the repository.

## Steps
1. Write `validate.js`, `tokens.js`, `emails.js` with tests first.
2. Write an in-memory `Store` and a recording `Mailer` in `test/worker/fakes.js`.
3. Write `handler.js` against the interfaces; test every row of the endpoint table, including:
   pending row not confirmed → no second email on a repeat within 10 minutes; confirm twice → second is "no longer valid"
   page; expired token (8 days) → invalid; unsubscribe deletes; rate limit trips on the sixth request; bad JSON; oversize
   body; wrong content type; unknown line; future priority date; challenge failure.
4. `purgeUnconfirmed`: a function `runMaintenance({ store, now })` that removes pending rows older than 7 days; tested.
5. `index.js` and `d1Store.js`: thin wiring only (they cannot be run here). Keep them short and obvious.
6. Confirmation email text (plain text, no tracking, no images): what was requested (category, area, chart), the confirm
   link, "If you did not ask for this, ignore this email; nothing will be sent again", and the site's postal-address
   placeholder `{{POSTAL_ADDRESS}}` (S-505 supplies it).
7. `worker/README.md`: owner deployment steps (create D1 database, apply `schema.sql`, set secrets, set the allowed
   origin, `wrangler deploy`), each as one command with placeholders. State clearly that an agent must not run them.
8. `npm run check`.

## Acceptance
- [ ] The four endpoints behave as in the table, proven by tests with fakes.
- [ ] Double opt-in: after `subscribe`, exactly one email (the confirmation) is sent and the row is `pending`.
- [ ] Stored fields are exactly the list above; unconfirmed rows are purged after 7 days by `runMaintenance`.
- [ ] Bot challenge and per-IP rate limit enforced; every input validated; responses do not reveal whether an email is subscribed.
- [ ] Tokens stored only as hashes; no secret, email or IP in logs or in the repository.
- [ ] A local mode exists (`worker/README.md` explains it) that prints emails to the console instead of sending.
- [ ] `npm run check` green; nothing deployed; no account created.

## Pitfalls
- Workers use Web Crypto (`crypto.subtle`), which Node 22 also provides globally. Do not import `node:crypto` in `worker/src`.
- Do not add an npm dependency for routing or validation; the handler is under 200 lines without one.
- Enumeration: any difference in response text, status or timing between "already subscribed" and "new" leaks who is on the list.
